# Rust/native design facts for Roost

Verified 2026-10-06 against official API documentation and first-party manifests. Planning evidence only: no application, platform runtime, authentication, or fault-injection tests were performed. The canonical Answers in [03](../issues/03-profile-compatibility.md#answer), [04](../issues/04-command-contract.md#answer), and [05](../issues/05-distribution.md#answer) govern; the proposals below are **candidates for decision 06**, not accepted choices. Repository-local decisions were reread rather than relying on older memory. The user's subsequent source-repository choice is [rmkr/roost](https://github.com/rmkr/roost); this note does not change the existing local checkout/remotes or claim that content has already moved there.

## Smallest feasible implementation

Candidate: one synchronous Rust binary, JSON registry/ownership records, one stable lock file per manager root, staged filesystem changes, and small Unix/Windows platform helpers. No daemon, OAuth client, supervisor, or async runtime is necessary. Prefer standard filesystem/process/terminal APIs; retain native bindings where they close a required safety gap.

| API/dependency candidate | Verified floor / qualification | Purpose |
| --- | --- | --- |
| `std::fs::File::{lock,try_lock,unlock}` | Rust **1.89** | Manager-root serialization; avoids a separate locking crate. [Rust File](https://doc.rust-lang.org/std/fs/struct.File.html#method.lock) |
| `std::io::IsTerminal` | Rust **1.70** | Terminal versus explicit stdin behavior. [Rust IsTerminal](https://doc.rust-lang.org/std/io/trait.IsTerminal.html) |
| `OpenOptions::create_new` | Rust **1.9** | Exclusive creation, including refusal of dangling destination links. [Rust OpenOptions](https://doc.rust-lang.org/std/fs/struct.OpenOptions.html#method.create_new) |
| Unix `OpenOptionsExt::{mode,custom_flags}` | Rust **1.0**, **1.10** respectively | Private creation and native no-follow flags. [Unix extensions](https://doc.rust-lang.org/std/os/unix/fs/trait.OpenOptionsExt.html) |
| Unix-only `rustix` | Current first-party manifest: 1.1.5, Rust **1.65** | Safe descriptor-relative `openat`/native operations when std pathname checks are insufficient. [Manifest](https://raw.githubusercontent.com/bytecodealliance/rustix/main/Cargo.toml), [openat](https://docs.rs/rustix/latest/rustix/fs/fn.openat.html) |
| Windows-only `windows-sys` | Current development manifest: 0.100.0, Rust **1.88**; not a released-version selection | DACL, handle attributes/identity, console and user PATH APIs. Recommendation: Rust 1.89 is sufficient for the listed stable std APIs; validate the actual dependency lockfile at the selected MSRV. A crate's development branch/version is evidence of its manifest, not proof of a published release or tested compatibility. Serialization crates are candidates, not a reason to invent a custom JSON parser.

## JSON state versus TOML state

No registry format has been accepted. `Cargo.toml` being required for source builds does not prescribe application storage: it is Cargo's package manifest. [Cargo manifest](https://doc.rust-lang.org/cargo/reference/manifest.html)

| Candidate | What it provides | Tradeoff |
| --- | --- | --- |
| Generated `registry.json` | Objects/arrays/null fit versioned machine-owned records and the already approved JSON output envelope | JSON has no standard comments; manual edits should be discouraged for ownership/recovery records. Reuses the JSON serialization dependency needed for CLI output. |
| Generated `registry.toml` | Readable tables and standard comments; viable for the same schema and lifecycle | Adds TOML serialization beside required JSON output. TOML has no null value: optional state uses omission/explicit discriminators. Ordinary serialize/overwrite does not promise preservation of hand comments. |
| Human `config.toml` plus generated registry | Useful if real user-editable preferences are later approved | No such new global configuration feature is needed by the selected command contract; adding one now creates an unrequested second source of truth. |

The syntax facts come from [JSON RFC 8259](https://www.rfc-editor.org/rfc/rfc8259) and [TOML 1.0 specification](https://toml.io/en/v1.0.0); candidate maintained libraries are [serde_json](https://raw.githubusercontent.com/serde-rs/json/master/Cargo.toml) and [toml](https://raw.githubusercontent.com/toml-rs/toml/main/crates/toml/Cargo.toml). Recommendation, not decision: generated `registry.json` has the smallest dependency/maintenance surface; `registry.toml` is equally feasible if the user prefers its presentation. Neither syntax supplies locking, atomicity, ownership authenticity, or recovery. Use exactly the same lifecycle invariants with either format and avoid naming machine-owned records `config` if that suggests supported hand editing.

## Filesystem and secret boundaries

`symlink_metadata` followed by ordinary `open`, `copy`, or `rename` leaves a check/use race. Canonicalization resolves redirection; it does not prove that the original root was not redirected or remain an authorization token. Root, ownership, token, and launcher checks must describe the opened object and its protected parent, not merely a prior pathname observation. Rust explicitly documents this distinction. [std filesystem TOCTOU](https://doc.rust-lang.org/std/fs/index.html#time-of-check-to-time-of-use-toctou)

Candidate Unix approach: anchor the real manager/source root with a directory descriptor; walk components relative to held directories with `openat`, directory/no-follow flags; inspect opened-object `fstat` metadata; read/copy from those handles. Check UID, private mode and link count for secret/ownership objects. New token files use 0600, private managed directories 0700; verify effective modes on the open object and refuse unsafe existing objects. Creation mode is masked by umask, so a secure requested mode is not a promise that all desired owner permissions survived. Unix `dev`/`ino` support physical-directory equality and `nlink` detects multiply linked regular files. [Unix creation modes](https://doc.rust-lang.org/std/os/unix/fs/trait.OpenOptionsExt.html), [Unix metadata](https://doc.rust-lang.org/std/os/unix/fs/trait.MetadataExt.html)

Candidate Windows approach: open root/parents as directories with `FILE_FLAG_BACKUP_SEMANTICS`; open examined final objects with `FILE_FLAG_OPEN_REPARSE_POINT`; reject **all** `FILE_ATTRIBUTE_REPARSE_POINT` objects at required roots/destinations and while copying. Junctions are only one reparse-point family. The no-follow flag on the final component does not itself prevent traversal through a redirected ancestor. Hold verified parent handles with appropriate sharing restrictions and recheck identity; the exact parent-walk/rename algorithm needs a Windows proof/test. Do not advertise a pathname-only algorithm as race-proof. [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [Reparse points](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-points), [Windows attributes](https://doc.rust-lang.org/std/os/windows/fs/trait.MetadataExt.html)

Windows `Permissions::set_readonly` does **not** establish confidentiality. Create token staging files with an explicit protected DACL for the current user before writing bytes, verify ownership/DACL on the open handle, and publish only after verification. Use `SECURITY_ATTRIBUTES` at creation or a nonsecret empty stage whose DACL is established before writing. Refuse null/unverifiable/permissive DACLs and filesystems without adequate security semantics. SYSTEM/administrator privilege and hostile same-user processes remain outside a private-file guarantee. Borrowed tokens are verified without repair. [Rust permissions](https://doc.rust-lang.org/std/fs/struct.Permissions.html), [Security descriptor creation](https://learn.microsoft.com/en-us/windows/win32/secauthz/creating-a-security-descriptor-for-a-new-object-in-c--), [SetSecurityInfo](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-setsecurityinfo)

Windows volume serial + file index can identify two paths to the same physical object; handle information can be partial/unsupported on some network configurations, so fail closed rather than assuming string inequality proves separation. Obtain link counts with native handle information where the chosen stable Rust metadata API does not provide it. [GetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfileinformationbyhandle)

For purge, prefer std `remove_dir_all` on the already verified owned directory over a handwritten recursive walker. Current Rust promises no symbolic-link following and protects symlink races on the selected Linux/macOS/Windows families; the documented exceptions are outside this matrix. This protects traversal, not the earlier ownership decision, and it can fail after partial deletion. Windows junction/other-reparse fixtures remain mandatory evidence. Copy uses a separate handle-based walk: skip links/reparse/multiply-linked/special files, and never open a skipped target. [Rust remove_dir_all](https://doc.rust-lang.org/std/fs/fn.remove_dir_all.html)

Required race bound: manager locking coordinates Roost instances using that root; it does not stop direct Claude/external writers or malicious same-user replacement. Protect parent namespaces from other users and use no-follow/handle checks. State explicitly which external races are excluded; do not weaken the approved no-contained-link-traversal rule to a preflight scan.

## Locking, publication, and recovery

Keep one stable, safely opened lock file; never delete/recreate it during normal operation, because participants must lock the same object. Hold its exclusive lock across a mutation and registry commit. Launch preparation briefly locks, validates/recover-checks metadata, obtains a safe token/environment snapshot, and spawns or prepares the child; release before waiting for Claude. Ensure no lock handle leaks/inherits into Claude. `try_lock` plus cancellable bounded polling can avoid an uncancellable wait. Same-root Roost processes serialize; separate roots do not imply coordinated overlapping upstream writers. [Lock semantics](https://doc.rust-lang.org/std/fs/struct.File.html#method.lock)

Candidate single-file commit: exclusive-create a private sibling temporary file, write complete versioned JSON, `sync_all`, then replace the verified registry in its same filesystem. `rename` can replace an existing target and cannot span filesystems; it is not a no-overwrite primitive and not a multi-file transaction. Define supported local-filesystem assumptions and platform replacement behavior. A file flush alone must not be described as universal power-loss durability of directory entries. [Rust rename](https://doc.rust-lang.org/std/fs/fn.rename.html), [sync_all](https://doc.rust-lang.org/std/fs/struct.File.html#method.sync_all)

Candidate multiartifact protocol: a persisted transaction intent records operation identity, owned staging paths, intended profile/launchers, and prior/new registry generations. Stage profile and every launcher fully; safely publish objects while the registration remains nonactive; atomically publish the active registry **last**; remove the intent after success. Every launcher consults the committed registry and rejects absent/pending/recovery state, preventing an early-published launcher from making an incomplete creation usable. A launcher missing during an incomplete mutation fails closed. Retained ownership evidence survives ordinary removal.

On restart, mutating operations under the lock classify an intent against committed generation and exact owned identities: finish bookkeeping of a committed transaction or clean/retain exclusively proven staging/uncommitted residue. Read commands/doctor report recovery without silently mutating. Any foreign replacement/collision yields refusal and explicit changed/retained state; no broad cleanup by filename prefix. Token replacement similarly leaves the old token intact until the new private file is safely published. Inject failure at each write/rename/registry/cleanup point, including partial purge and Windows sharing denial. This is a recommended recoverable protocol, not a claim of multiartifact filesystem atomicity.

## Launcher binding and native forwarding

Required wrappers bind **absolute selected Roost executable + absolute manager root + profile/registration identity**, and call the common safety/launch path. They must not select `roost` through PATH, assign `ROOST_DIR` to bind storage, or infer only `NAME` from their basename: those fail foreign-PATH, alias-environment, and same-name/multiple-root cases. `current_exe` supplies a full path but has documented platform/security caveats; it is not executable authenticity. Store/verify the selected path under ordinary same-user installation assumptions. Missing/relocated/foreign bindings fail with `reuse`/registration-refresh guidance; no PATH fallback. [current_exe](https://doc.rust-lang.org/std/env/fn.current_exe.html)

**Design choice requiring explicit approval in ticket 06:** use a hidden internal launcher transport in the same binary, or add a dedicated sidecar binary. Public `run` has no root-binding option and intentionally consumes one initial delimiter, whereas launchers must consume no caller arguments. Candidate smallest transport: generated wrappers pass a versioned private dispatch selector plus fixed root/registration operands, followed by a fixed transport boundary and the untouched caller argument tail. The internal path does not parse caller manager flags and does not strip a caller leading `--`. The selector is an implementation protocol, omitted from public help, not a quietly added public command. Validate all binding operands with the same ordinary safety rules; hidden dispatch is not privileged authorization.

Do not use an internal environment variable without provenance/restoration: any name can already exist in the caller environment, and deleting it before child launch also changes the approved alias environment. Command operands avoid that problem. Hardlink/copy/same-binary argv0 dispatch alone does not encode root identity reliably and does not satisfy the already selected sh/.cmd/.ps1 forms; per-profile binary copies also add upgrade/staleness burden.

POSIX sh wrapper candidate: quote fixed literals once and forward `"$@"` to the absolute manager; use `exec` so the wrapper does not become a second waiting parent. Fish callers can execute that shebang launcher; no separate Fish profile function is needed. At the manager boundary, retain `OsString` values, cwd, inherited stdio and caller environment; isolated child changes only approved entries, alias child changes none. `Command::spawn/status` inherit stdio; `output()` is unsuitable for interactive run/update. [Rust Command](https://doc.rust-lang.org/std/process/struct.Command.html)

Windows native EXE arguments use the normal runtime encoding; `cmd.exe`/batch have different grammar and injection risks. Prefer a discovered native Claude executable; do not run arbitrary Claude arguments through `raw_arg` or a generic `cmd /c` formatter. A PATH-resolved `.cmd` Claude shim needs an explicitly tested safe adapter or an unsupported-installation refusal with native-install guidance—this is an unresolved compatibility detail, not permission to silently bypass the selected installation. [Windows CommandExt](https://doc.rust-lang.org/std/os/windows/process/trait.CommandExt.html#method.raw_arg)

PowerShell 7.3 changes native argument passing and preserves cases legacy 5.1 loses, including empty arguments and embedded quotes; PS7 Windows mode still uses legacy behavior for `.cmd`. A simple `& $exe @args` cannot establish the full PS5.1 preservation promise. Candidate `.ps1` adapter explicitly encodes the received string array with Windows runtime quoting using `ProcessStartInfo` without shell execution; use `ArgumentList` where available and a tested `Arguments` encoder on the required legacy runtime. Verify inherited handles, cwd, cancellation and exit status rather than assuming the adapter works. [PowerShell parsing](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_parsing?view=powershell-7.5), [.NET ArgumentList](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.processstartinfo.argumentlist?view=net-10.0)

For `.cmd`, fixed literals require batch-specific escaping; delayed expansion must not corrupt `!`, and avoid `CALL` reparsing of arbitrary arguments. `%*` is raw forwarding, not a typed argv array; the native shell's initial interpretation cannot be undone. State preservation at the received-argument boundary and test literal metacharacters/quotes/empty values in required shells. Git Bash/MSYS also converts apparent Unix paths and environment path values when invoking native programs; changing `MSYS2_ARG_CONV_EXCL` globally would violate caller-environment preservation. Document native caller quoting/conversion controls, and test representative Claude path arguments. [Microsoft CALL](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/call), [MSYS path conversion](https://www.msys2.org/docs/filesystem-paths/)

## Cancellation and required evidence

Before handoff, a cancellation flag restores terminal mode, leaves prior token intact and returns 130. For interactive native children, keep the shared foreground console/process group so normal terminal Ctrl+C reaches the child; manager survives long enough to wait and return its result. Do not double-send a terminal event already delivered. Programmatic targeted Unix signals and Windows console events require platform-specific behavior. Windows `GenerateConsoleCtrlEvent` has restrictions: CTRL+C cannot be reliably targeted to an arbitrary group; CTRL+BREAK is a different event. `Child::kill` is termination, not graceful Ctrl+C, and neither a console event nor std Child promises whole-tree cleanup. No new supervisor guarantee is required. [Console handlers](https://learn.microsoft.com/en-us/windows/console/console-control-handlers), [GenerateConsoleCtrlEvent](https://learn.microsoft.com/en-us/windows/console/generateconsolectrlevent)

Acceptance must use a native argument/environment/stdio probe before live Claude: leading `--`, `--help`, `--allow-auth-env` literals, empty arguments, Unicode, spaces, quotes, trailing backslashes, `&|<>^%!`, path-looking Git Bash values; original `ROOST_DIR` absent/empty/other-root; two roots with the same NAME; foreign PATH Roost; custom Cargo root; relocated/missing/replaced manager; default alias exact environment; redirected root/token/launcher; dangling links, Windows junctions/reparse points, hardlinks; private new/replaced token and borrowed-token refusal; per-root concurrent mutation with simultaneous long-lived children; interruption at every publication point; and cancellation before/during child launch.

Run that evidence on x86_64/ARM64 Linux glibc/musl, macOS, native Windows and separate WSL2, with the approved Bash/Zsh/Fish and PS5.1/PS7/CMD/Git Bash matrix. Build success is not runtime evidence. No factual blocker requires a new ticket yet: hidden transport and Windows shim/wrapper details belong to ticket 06. If targeted probes cannot satisfy an approved forwarding guarantee, record the precise incompatible shell/install case and return that conflict to the human before declaring the specification ready.
